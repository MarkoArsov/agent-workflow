# Required routing scenarios

These are fixture contracts for the improved evaluator, not claims about actual
account access, price or current successful model generation. Use synthetic model
IDs with distinct lab lineage and reviewed simple/balanced/demanding mappings.
Do not pin routes unless the scenario explicitly calls for a real user/project pin.

| Fixture | Expected behavior |
| --- | --- |
| Routine tests, 650 estimated lines | Strong capability, balanced effort; size advisory, no automatic deep/high escalation. |
| Complex uncertain implementation, routine tests | Deep/demanding implementation, strong/balanced tests; stage inputs do not spread. |
| High-risk review, routine complexity, no uncertainty | Deep capability with balanced effort, when supported; band and effort have separate explanations. |
| Simple bounded documentation stage | Lowest adequate fast model and simple effort mapping. |
| Planner suggests an unavailable cheap model | Exclude it; preserve eligibility requirements and choose a reviewed available alternative or unresolved. |
| Planner suggests a model while project pins another | Preserve project pin and explain project provenance; suggestion is not authorization. |
| Two eligible labs | Prefer the alternate lab for adversarial stages within the policy's capability bounds; explain remaining collisions with only two labs. |
| Missing catalogue and valid configured default | Retain it as a default, display missing evidence, never label it adaptive selection. |
| Missing catalogue and no configured route | Unresolved; never fabricate access or pick from seed names alone. |
| Unsupported effort or maximum effort mapping | Omit unknown effort with a reason; no automatic xhigh/max/ultra. |
| Saved 1.0 or 1.1 snapshot | Validate original hash/routes without re-running new selection rules. |
| Project adaptive defaults after migration | Both providers allowed; released stages have defaults and no effective pins; fixture resolution never reads the developer's global settings. |

Assertions compare chosen model family, effort, origin and exclusion reasons; they
must not mirror candidate-sort implementation or make live provider/network calls.
